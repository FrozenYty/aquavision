# 装置控制器

> 本文为 `firmware/README.md` 的中文对照版，以英文版为准。

`main/` 里的 ESP32-S3 是整套装置上人会碰的那一部分。它上报按键按下，读取浊度传感器，在
0.96 寸 OLED 上显示最近一次采集的判定，并点亮两颗 LED 中的一颗。

它**不采图，也不做推理**。这两件事都归 PC，而一帧画面的质量只有 PC 说了算——固件只显示被
告知的内容。

## 状态：草稿

屏幕布局是**初稿**，2026-11-07 商定，从未在真实面板上看过。在装置上台架之前，`src/screen.cpp`
里的每一个坐标都是暂定的。

## 各部分在哪

| 文件 | 负责什么 | 什么时候改 |
|---|---|---|
| `src/config.h` | 引脚、时序、I2C 地址 | 挪了一根线，或某个周期感觉不对 |
| `src/rig_state.h` | 装置知道的东西：屏幕、分数、浊度、趋势 | 有新的值需要被记住 |
| `src/screen.cpp` | 128×64 的布局，每个状态一个函数 | 屏幕该换个样子 |
| `src/protocol.cpp` | 串口语法 | PC 和板子之间要说一句新的话 |
| `src/main.cpp` | 调用上面四个的循环 | 几乎从不改 |

新增一个屏幕状态要改三处：在 `rig::Screen` 里加一项，在 `screen.cpp` 里加一个 `drawX` 函数，
在 `render()` 里加一个 `case`。往显示上加一个字段，是在 `rig::State` 里加一行、在画它的那个
函数里再加一行。固件里没有别的地方知道像素这回事。

## 编译与烧录

```
cd firmware/main
pio run                 # compile
pio run --target upload # flash
pio device monitor      # watch the protocol
```

PlatformIO 会按锁定的版本拉取 U8g2。如果没装 `pio`：

```
python -m pip install platformio
```

## 接线

| 信号 | ESP32-S3 | 说明 |
|---|---|---|
| 按键 | GPIO 4 | 接 GND；`INPUT_PULLUP`，所以按下读到 LOW |
| 绿色 LED | GPIO 5 | 串联电阻 330 Ω |
| 黄色 LED | GPIO 6 | 串联电阻 330 Ω |
| OLED SDA | GPIO 8 | I2C，地址 0x3C |
| OLED SCL | GPIO 9 | I2C |
| 浊度 SDA | GPIO 8 | 同一条总线，地址 0x49 |
| 浊度 SCL | GPIO 9 | 同一条总线 |

两颗 LED 都需要电阻。三个 1 kΩ 电阻并联是 333 Ω，够接近了；如果零件盒里本来就有一袋 1 kΩ，
这样就不必再买任何东西。

## 屏幕

128 x 64，单色，五条带；各条的基线都是具名常量，所以状态之间不会有东西挪位：

```
y 1..7    AQUAVISION                                  ONLINE        disc on the caps' centre row
y 8       -------------------------------------------------------
y 12..31                              94                            18 px score, right-aligned
          QUALITY                                                   7x13 bold label, rows 17-26
y 33..53  +-----------------------------------------------------+
          |                       RETAKE                        |    filled = PASS, outline = RETAKE
          +-----------------------------------------------------+
y 54      -------------------------------------------------------
y 55..62  TURB 12400                                  FRAMES 12
```

**形状承载判定。** 通过时横幅填满，重拍时只描边，所以隔着房间、一个字还看不清的时候，两者就
已经能区分。分数那一行的标签，通过时是 `QUALITY` 这个词，重拍时是原因——正因为如此，横幅才能
缩成一个词，而不必把两行字叠进二十个像素里；那样两行之间只剩一个像素，读起来像一团污渍。

**标签和数字共用一条中心线。** 在面板上实测：分数数字的字形自报 ascent 19，所以在基线 31 上
它占 12-31 行；粗体 7x13 的标签自报 ascent 9，所以在基线 26 上它占 17-26 行。两者的中心都落在
21.5。5x7 的标签放在同一基线上会低 1.5 px。

**页脚只用一个留白宽度。** 标签、六个像素、值——两栏相同。浊度值在这段留白之后左对齐，因为
右对齐会让五位读数后面留两个像素的缝隙、三位读数后面留一条很宽的缝隙：同一行里两种不同的
缝。占位符是五条短横，与读数的宽度一致，所以数据到达时这一行不会跳。

**没有分数的状态用那条空出来的带。** `READY` 在这里放 `PRESS TO CAPTURE`，`CAPTURING` 放三个
点，每四分之一秒亮一个。在 3 像素的尺度上，实心标记与空心标记无法区分；半径取 2 时，这段动画
才读得出来。`OFFLINE` 把整屏换成三行居中文字——早先那一行 12 px 的字比面板还宽，最后几个字母
被截掉了。

**没有趋势标记。** 代码原来会画一个三角形表示上升、下降、持平，用绝对阈值判定：两个计数，而
读数跨度是 700-16000。在那个量级上，两个计数就是噪声，所以标记会闪；而读数到五位数时，它还
会和 `FRAMES` 撞在一起。值得显示的趋势必须是相对量，而在有理由做之前，直接显示读数本身才是
诚实的做法。

## 串口协议

一行一条消息，ASCII，以 `\n` 结尾。固件忽略它看不懂的任何内容，所以一个乱码字节不会让装置变砖。

| 方向 | 消息 | 含义 |
|---|---|---|
| → PC | `EVT HELLO <version>` | 板子起来了 |
| → PC | `EVT I2C <addr>` | 开机扫描时每个应答的设备一行 |
| → PC | `EVT SCREEN <name> <score>` | **每一次**屏幕变化：READY、CAPTURING、PASS、RETAKE、OFFLINE |
| → PC | `EVT TRIGGER <millis>` | 按键被按下，一次采集开始了 |
| → PC | `EVT TURBIDITY <value>` | 每 5 s 一次的新读数 |
| → PC | `EVT TIMEOUT <millis>` | 5 s 内没有等到判定，所以这一张算 RETAKE |
| → PC | `EVT STRAY RESULT <score>` | 没有在途采集却来了判定；该判定**没有**被采用 |
| → PC | `EVT PONG` | 对 `CMD PING` 的应答 |
| PC → | `CMD RESULT <score> <PASS\|RETAKE> <REASON>` | 要显示什么，仅在 CAPTURING 时有效 |
| PC → | `CMD READY` | 回到空闲屏幕 |
| PC → | `CMD PING` | 存活检查 |

`REASON` 是一个 token：`LOW_LIGHT`、`BLUR`、`COLOR_CAST`、`NONE` 或 `NO_REPLY`。最后一个是
装置自己生成的，永远不会发给装置。

**PC 那一半现在有了**（`server/app/rig/`，P2-17）：服务端打开端口，每两秒发一次 `CMD PING`，
把 `EVT TRIGGER` 变成一次采集和一条 `CMD RESULT`，并记录装置上报的每一次屏幕变化。它自己的
状态机，以及采集失败时*什么都不发*的理由——装置随后超时会报 `NO REPLY`，而那正是事实——都在
`docs/rig-state-machine-zh.md` §9。

**链路由 PC 负责，沉默就意味着它不在了。** 装置看不出 USB 线插没插——它经桥接芯片走 UART，
没有载波信号——所以存活是协议层面的事：**只要链路开着，PC 就必须至少每两秒发一次
`CMD PING`**，而装置在十秒没有收到命令之后宣布 `OFFLINE`（漏掉五次保活）。

装置开机停在 `READY`，带十秒宽限，这远长于 PC 发出第一次保活所需的时间。一块面板在任何
东西有机会开口之前就宣布自己死了，读起来像故障，而不像在等待。从那时起，两者成对——`OFFLINE`
当且仅当链路不在——而一台空闲的装置之所以停在 `READY`，只是因为 PC 一直在这么说。台架上没有
PC 软件的装置会在上电十秒后变成 `OFFLINE`，这是对的：另一头没有人。`rig::invariantHolds` 每一
轮循环都检查这组配对，一旦被破坏就上报 `EVT INVARIANT`。

**判定是一次采集的答案，所以只在采集在途时接受。** 其它任何状态下的 RESULT 都会被丢弃，并上报
`EVT STRAY RESULT`；这里选择告诉 PC，而不是让它以为装置收下了。背后的规则，以及每一个状态/事件
组合，都在 `docs/rig-state-machine-zh.md`。

## 到货的那块板子定下了什么

第一块板子于 2026-11-10 烧录，第一个假设没有成立。`Serial` 指向了 S3 的原生 USB 口，于是 UART
桥只显示 ROM 的启动信息、没有任何来自 sketch 的输出——一块跑得好好的板子看上去像死的。现在
`ARDUINO_USB_CDC_ON_BOOT` 是 0，把 sketch 放到 UART0 上：一根线既能烧录也能监视，而且不需要按
BOOT 键。

`setup()` 还会扫描一次 I2C 总线，每个应答的设备打印一行 `EVT I2C <addr>`。这样，缺一块屏或者
传感器没插，就会出现在串口日志里，而不是只表现为一块空白屏——装配阶段这是最快的检查。

在板子上验证过：镜像能烧入并通过校验，固件打印 `EVT HELLO 1.1`，而没有接任何东西时 I2C 扫描
什么也不报。

**打开串口会让板子复位。** 桥接芯片的 DTR 与 RTS 接了自动复位电路，所以任何程序一打开 `COM5`，
固件就会重启——日志从头是 ROM 启动信息，随后是一条全新的 `EVT SCREEN READY`。**这是板子在正常工作**，
但调试前值得先知道：一个连上端口后再等十一秒的读取程序，会看着装置变成 `OFFLINE`，因为**开机先发生，
而十秒的链路计时也从那一刻开始**。要测保活，就在**保持打开的端口上**测，不要靠反复重连。

对工具有两个后果。台架检查一旦打开端口就退出，留下的是「刚开机」的装置，而不是它原本的状态。
而重启服务端等于重启板子：链路不是「重连」，是从头开始。

**OLED 已验证。** 直接接在 ESP32 上——`VCC` 接 `3V3`、`SDA` 接 `GPIO8`、`SCL` 接 `GPIO9`——
扫描报 `EVT I2C 3C`，开机画面画出来了，`CMD PING` 也答了 `EVT PONG`，所以从 PC 到板子的命令
通路和显示一样是通的。随后在没有按键的情况下从串口驱动了五个屏幕：
`CMD RESULT 94 PASS OK`、`CMD RESULT 30 RETAKE LOW_LIGHT`、`CMD RESULT 55 RETAKE COLOR_CAST`、
`CMD RESULT 20 RETAKE UNKNOWN`，以及干脆沉默到十秒超时得到的 `OFFLINE`。

**尚未验证：** 两颗状态 LED，因为 330 ohm 电阻还没到；按键，它也还没到；以及浊度传感器，它得
先有电平转换板。

## 硬件参考

支撑这套装置的三份厂商文档**不在本仓库里**：仓库是公开的，而浊度传感器手册禁止未经书面同意
向第三方披露。从文档里学到的事实可以记录下来，文档本身不能转载。硬件负责人手上有副本，需要
时可以索取。

| 文档 | 型号 | 定下了什么 |
|---|---|---|
| 厂商数据手册 | ESP32-S3-WROOM-1 | GPIO 为 3.3 V，每个引脚最大驱动 40 mA |
| 模块数据手册 | 0.96 寸 128x64 OLED，SSD1306 | I2C 地址 `0x3C`，供电 2.8–3.3 V——3V3 这条轨是对的 |
| 传感器手册 A3 版 | ME2100A-IIC 浊度传感器 | **供电 4.5–5.5 V**，地址 `0x49`，清水读数高，浑水读数低 |

最后一列是这个项目实测或读到、并决定依赖的内容。不在仓库里的文档不能用文件名来引用：**别人
磁盘上的一个 PDF 名字，和一条路径一样不可移植**，而打不开这个文件的读者，知道它叫什么也毫无
收获。

**浊度传感器是 5 V 器件，这改变了接线。** A3 版删掉了早前版本所带的 3.3 V 规格，它的接口能
承受最高 5.5 V——ESP32 不能。SDA 与 SCL 上必须加电平转换，**这是必需项，不是可选项**；装配
方案此前把它当成可以跳过的一步。

## 仍未验证

1. **浊度值住在哪个寄存器里，还不知道。** 手册描述了怎么读一个寄存器——起始、写地址、命令
   字节、重复起始、读地址、数据——但从没说是哪个寄存器存放测量值。`readTurbidity()` 目前是
   一次裸的两字节读，不带命令字节，依赖器件指针本来就停在测量值上。地址和两字节宽度现在已
   确认；寄存器还没确认。等传感器接好后用实测来定：先试裸读，再试写入命令 `0x00`–`0x03` 之后
   的读，保留那个数值随水变浑而下降的。屏幕上出现一个看似合理但错误的数值，比没有数值更糟。
