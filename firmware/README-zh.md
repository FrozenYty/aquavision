# 装置控制器

> 本文为 `firmware/README.md` 的中文对照版，以英文版为准。

`main/` 里的 ESP32-S3 是整套装置上人会碰的那一部分。它上报按键按下，在 0.96 寸 OLED 上显示最近一次
采集的判定，并驱动一块四位数码管显示。这里已经没有浊度传感器，也没有状态灯：传感器于 2026-11-14
拆除，因为它的任何一个寄存器都不跟随水体变化（证据记在 `P3-37`），而三盏灯原来占的引脚现在是数码管
的公共端。

它**不采图，也不做推理**。这两件事都归 PC，而一帧画面的质量只有 PC 说了算——固件只显示被
告知的内容。

## 状态：OLED 已在面板上跑过，数码管尚未接线

屏幕布局是**初稿**，2026-11-07 商定。那块屏已在 2026-11-10 接到板子上并驱动过五个屏幕（见「到货的
那块板子定下了什么」），但整套装置尚未组装：在它上台架之前，`src/screen.cpp` 里的每一个坐标仍是
暂定的。

四位数码管目前只存在于固件里。它的画面跑在 `main.cpp`，引脚声明在 `config.h` 里；把它接到台架上，
是 `P3-17` 的事。

## 各部分在哪

| 文件 | 负责什么 | 什么时候改 |
|---|---|---|
| `src/config.h` | 引脚、时序、I2C 地址 | 挪了一根线，或某个周期感觉不对 |
| `src/rig_state.h` | 装置知道的东西：屏幕、分数、原因、帧数、故障、链路 | 有新的值需要被记住 |
| `src/screen.cpp` | OLED 的 128×64 布局，每个状态一个函数 | 屏幕该换个样子 |
| `src/presentation.cpp` | 第三台状态机：两块屏各画哪张脸，以及「在等 PC」是什么意思 | 状态、事件或脸发生变化（`docs/rig-state-machine-zh.md` §11） |
| `src/protocol.cpp` | 串口语法 | PC 和板子之间要说一句新的话 |
| `src/main.cpp` | 主循环、按键、数码管的各个画面，以及复用它们的定时器 | 几乎从不改 |

新增一个屏幕状态要改五处：在 `rig::Screen` 里加一项，在 `screen.cpp` 里加一个 `drawX` 函数，
在 `render()` 里加一个 `case`，在 `main.cpp` 的 `screenFace()` 里加一个 `case` 让面板有对应画面，
还要在 `protocol.cpp` 的 `screenName()` 里加一个 `case`，让 PC 收到一个它认识的名字。往 OLED 上加
一个字段，是在 `rig::State` 里加一行、在画它的那个函数里再加一行。固件里没有别的地方知道像素这回事。

## 编译与烧录

两个环境，一根线一个（`docs/rig-transport-en.md` §11）：`rig-serial` 是线缆与台架，`rig-ble` 是成品
装置，而且它什么都不往 UART 写。

```
cd firmware/main
pio run -e rig-serial                  # compile the cable build (the default)
pio run -e rig-serial --target upload  # flash it
pio run -e rig-ble                     # compile the Bluetooth build
pio run -e rig-ble --target upload     # flash it
pio device monitor                     # watch the protocol; the serial build only
```

**串口版是作为一个目标活下来的，不是作为一段文字。** 射频出问题必须只花三十秒和一根线，而不是花掉演
示：烧 `rig-serial`、插上线、把服务指向一个 COM 口。只有这个目标一直在编译、一直在被使用，上面这句话
才成立，所以台架上的活归它。

PlatformIO 会按锁定的版本拉取 U8g2。如果没装 `pio`：

```
python -m pip install platformio
```

## 接线

| 信号 | ESP32-S3 | 说明 |
|---|---|---|
| 按键 | GPIO 4 | 接 GND；`INPUT_PULLUP`，所以按下读到 LOW |
| 数码管 A 段 | GPIO 3 | 引脚与段之间串 330 Ω |
| 数码管 B 段 | GPIO 13 | 同上 |
| 数码管 C 段 | GPIO 14 | 同上 |
| 数码管 D 段 | GPIO 15 | 同上 |
| 数码管 E 段 | GPIO 16 | 同上 |
| 数码管 F 段 | GPIO 17 | 同上 |
| 数码管 G 段 | GPIO 18 | 同上 |
| 数码管第 1 位（左） | GPIO 5 | 公共端，直连：不串电阻 |
| 数码管第 2 位 | GPIO 6 | 同上 |
| 数码管第 3 位 | GPIO 7 | 同上 |
| 数码管第 4 位（右） | GPIO 10 | 同上 |
| OLED SDA | GPIO 8 | I2C，地址 0x3C |
| OLED SCL | GPIO 9 | I2C |

**这块面板是共阳的，这决定了高电平意味着什么。** 某一位的公共端拉高就选中那一位，段引脚拉低才点亮
该段，所以**不亮的段是高电平引脚**——与直觉接法相反，点不亮之前先查这一条。

每一段在引脚与段之间各有一只 330 Ω 电阻，公共端一只也没有。因此一条公共端承受的是它这一位上各段
电流之和，而**任何时刻只能有一条公共端为高**——这正是 `main.cpp` 里的复用器所保证的。

面板上的每一个引脚都是 GPIO，所以它经这些引脚吃主板自己的 3.3 V：数码管上没有供电引脚，这套接线里
也没有 5 V 轨。

## OLED 屏

128 x 64，单色，五条带；各条的基线都是具名常量，所以状态之间不会有东西挪位：

```
y 1..7    AQUAVISION                                      ●              只有心跳点
y 8       -------------------------------------------------------
y 12..31                              94                            18 px score, right-aligned
          QUALITY                                                   7x13 bold label, rows 17-26
y 33..53  +-----------------------------------------------------+
          |                       RETAKE                        |    filled = PASS, outline = RETAKE
          +-----------------------------------------------------+
y 54      -------------------------------------------------------
y 55..62  version                                   FRAMES 12
```

**形状承载判定。** 通过时横幅填满，重拍时只描边，所以隔着房间、一个字还看不清的时候，两者就
已经能区分。分数那一行的标签，通过时是 `QUALITY` 这个词，重拍时是原因——正因为如此，横幅才能
缩成一个词，而不必把两行字叠进二十个像素里；那样两行之间只剩一个像素，读起来像一团污渍。

**标签和数字共用一条中心线。** 在面板上实测：分数数字的字形自报 ascent 19，所以在基线 31 上
它占 12-31 行；粗体 7x13 的标签自报 ascent 9，所以在基线 26 上它占 17-26 行。两者的中心都落在
21.5。5x7 的标签放在同一基线上会低 1.5 px。

**页脚是固件版本与帧数。** 左边是版本号，由 `EVT HELLO` 发送的同一个常量拼出来，所以面板与日志不会
对「跑的是哪个构建」各说各话；右边 `FRAMES 12` 是真实的采集计数。会话计数已经没有了——判定次数是统计
数据，记录在 PC 那边。

**没有分数的状态用那条空出来的带。** `READY` 在这里放 `PRESS TO CAPTURE`，`CAPTURING` 放一排六个点，
每四分之一秒亮一个，与面板上那段旋转共用同一个相位的一步（`cfg::DISPLAY_ROTATE_STEPS`）。那六个点是面板的
边框段：面板转几个边框段就有几个点，所以点行与段不可能对不上。在 3 像素的尺度上，实心标记与空心标记无法
区分；半径取 2 时，这段动画才读得出来。

**上电时若没有中心设备连着，OLED 就是房内状态脸，只把标题换成 `WAITING`，没有任何东西在动。** 这就是
表现层的 `Pairing` 脸（`docs/rig-state-machine-zh.md` §11）：装置还没有 PC，而且没有出任何问题。`WAITING` 与
`RADIO FAULT` 由同一个 `drawStatusFace` 画出——同样的反色框、同样的 `AQUAVISION` 页眉、同样的基线、同样的
正文行，以及同样的 Helvetica 粗体 12 标题——因为它取代的十二格进度行暗示了一种并不存在的进度，而误导性的指示比
没有更糟。**标题是 `WAITING` 而不是 `WAITING FOR PC`，原因是字符数，不是字体**：十三个字符在 128 px 面板上放不进
粗体 12，而为塞下它们缩小字号，正是这张脸显得空的原因。七个字符的标题用房内字号，加上正文行 `NO LINK TO PC`，
读作「在等——还没有连上」。面板画 `APP`，第四位以与 `CAPTURING` 相同的 250 ms 步长、通过同一个
`presentation::rotationStep` 走过六段边框，所以两张脸不可能对不上。**哪里都没有位置表**：它取代的环是十二项的表，
一个错对让第四位底边亮了两次、第一位底边从不出现；现在步进是 `1u << step`，位移没有条目可以写错。

**`OFFLINE`、`Err0` 与 `NoLink` 状态已退役。** 在 BLE 里链路就是结束，装置重新可用；而在听的订阅者不再说话时，
处置与从未连上的那个相同——等。两张脸对同一个处置，只会让操作员多绕一步，而 `Err0` 还把「等待」叫成故障。于是
安静下来的订阅者留在 `Live`，看到的是装置自己的屏幕。**`Err0` 的编号不再复用**：其余代码保持 `Err1`-`Err4`，
这个空号不花任何代价。OLED 页眉也不再写链路名：安静的同伴不是故障，右边只剩心跳点。
`rig-serial` 上永远不会出现 `Pairing`：UART 没有载波信号，永远回答在听，所以串口构建以 `Live` 起步并留在那里。

**`Pairing` 的意思是「没有人在听」，而按键读的是同一个事实。** `transport::listening()` 是 BLE 层的
`Streaming`，不是「有中心设备连着」：一个已经连接但还没打开通知的中心设备听不到 `EVT TRIGGER`，把它当成 PC 会
让一次按键启动没人收到的采集，四秒后再报 `NO REPLY`——那是在说一台从未听到触发的 PC 没有回答。把 `Live` 键在
`Streaming` 上，这段窗口就落进 `Pairing`，拒绝在那里是**可见的**——操作员看到的就是 `WAITING` 和 `APP`。这也是
为什么接受条件与画脸条件故意是同一个条件：`presentation::state() == Live`（`docs/rig-state-machine-zh.md` §11
规则 7）。安静下来的订阅者是另一件事：它在 `Live` 里会采集，而 `Err1` 报告持续四秒的沉默。

**无法广播的射频是 `Pairing`，不是 `Err4`。** `Advertising` 会一直重试，所以还没成功广播的装置就停在 `WAITING`、
`APP` 在转。这是诚实的——还没有人在听——而 `Err4` 留给拒绝启动或到达掉线风暴的射频栈，那种情况等是修不好的。
代价是一台永远哑掉的射频在玻璃上看不见，只有在写下来之后这代价才可以接受（`docs/rig-state-machine-zh.md`
§11 规则 14）。

**这张脸是静态的，进入时发一次。** 没有逐步重画，也没有局部 tile 更新——那条路径是这次改动里唯一写入少于整块缓冲
的地方，也正是把屏幕画花的原因——所以唯一能重画等待脸的就是别处来的脏标记，而心跳在 `Live` 之外已经不再标脏。
面板掩码由主循环发布，OLED 模块从不碰它；旋转也**没有**放进中断：I2C 会阻塞，等总线的 ISR 会把它要保护的那块屏
拖住。

## 四位数码管

**节奏是一条规则，而不是一组数字：正在工作的以稳定节奏走，失败了的以警示节奏闪，而台面仪器上的
任何东西都不超过大约 1 Hz。** 下面的每一个速度都从它推出来：`RETAKE` 与每一个故障代码都以 1 Hz 闪烁，
所以代码与分数是靠它写的内容分清的，不是靠节奏。

**四位数字，任何时刻只亮一位，由硬件定时器切换而不是由主循环切换。** 面板每 250 µs 刷新一位，
整个画面约 1 kHz——高于眼睛能看见的频率，这正是四位复用的数字能被读成四个稳定数字的原因。为什么
放进定时器：一次 OLED 传输会把主循环堵住 20-25 ms，而由主循环驱动的面板在这段时间里只以满占空比
显示一位，在会动的画面上看起来就是闪。现在主循环只算出四位各自的段码，在临界区里发布；定时器中断
每次读一位段码、写 GPIO 寄存器，两者都不会读到对方写了一半的状态。

**画面只按自己的年龄走。** 开机序列结束与任何一次换屏都会把这个年龄从零开始，所以没有任何画面会继承
上一块面板的相位；故障的年龄也是它自己的相位，所以闪烁随故障开始。两块屏读同一个开机时钟：OLED 把开机
画面一直压到面板两秒自检结束，两者一起进入 `READY`。这道钳位是因为一个真实缺陷才有的：没有它，空闲周期
会从自检停下的地方接着走，每次上电后的第一条横杠就落在第 2 位而不是第 1 位。

| 画面 | 显示什么 | 时序 |
|---|---|---|
| 开机 | 逐段扫过全部 28 个位置，然后 `8888`，然后全灭 | 每位置 25 ms（共 700 ms）、300 ms 的 8、1000 ms 全灭：共 2 秒，只做一次 |
| `Pairing` | `APP`，第四位在六段边框上旋转 | 每步 250 ms，六步一圈 |
| `READY` | 一条横杠（只有 G 段），走过第 1、2、3、4 位，然后从第 1 位重新开始 | 每位 500 ms，一周期 2 秒 |
| `CAPTURING` | `CAP`，第四位上有一段沿边框转圈 | 每步 250 ms |
| `PASS` | 从左到右扫过一次，然后分数占第 1-3 位、`P` 占第四位：` 95P` | 进场扫过 250 ms，随后常亮 |
| `RETAKE` | 分数与 `F`，整块面板闪烁：` 40F` | 1 Hz |
| 故障 `Err1` | 采集超时，闪烁 | 1 Hz，持续 2 s |
| 故障 `Err2` | 无对应采集的判定，闪烁 | 1 Hz，持续 2 s |
| 故障 `Err3` | 不变式被破坏，闪烁 | 1 Hz，持续 2 s |
| 故障 `Err4` | 射频失效，闪烁 | 1 Hz，且没有窗口：直到断电重启或重新烧录 |

**`Pairing` 画的是 `APP` 加一个旋转的第四位，不是一个代码，也不是 `READY` 走带。** 没有中心设备连着时，没有故障
可报：装置已经就绪，不同的只是链路细节。这个词命名的是操作员即将打开的 PC 端应用——正是这个状态在等的动作——第四位
以与 `CAPTURING` 相同的 250 ms 步长、通过同一个 `presentation::rotationStep` 走过六段边框。两半都是这块面板已经
画过的东西，这是有意的：操作员在采集时已经见过的同一个旋转表示「还在工作」，词则说明该做什么。**哪里都没有位置
表**——它取代的环是十二项的表，一个错对让第四位底边亮了两次、第一位底边从不出现，于是一个位置消失、另一个停留
过久；现在步进是 `1u << step`，位移没有条目可以写错，检查断言的是定义（六个位置、六段互不相同、没有重复）而不是
表的副本。**区别是形状，不是方向**：第一版把 `READY` 走带反过来走，台架否掉了，因为两条横杠朝相反方向移动，一眼
看去没有区别。安静下来的订阅者不是第三张脸：装置留在自己的屏幕上。这个区分是表现层的
（`docs/rig-state-machine-zh.md` §11），也正是台架上上电的装置不再对着空气闪故障的原因。

**`READY` 是一条单向走带。** 第 1、2、3、4 位，然后直接回到第 1 位，每位半秒：一周期两秒，没有全黑帧，也从不同时
亮两条横杠。**这个回绕是故意的**——横杠在第 1 位重新开始，而不是掉头往回走，所以这一屏是一条带可见断点的传送带，
`config.h` 里写着不要把它「修」成来回弹。更早的版本是四条横杠一起保持一秒；走带取代了它。

**`Err1`-`Err4` 是故障窗口，它们看起来一样。** 每个代码都以 1 Hz 闪烁——代码就是标识，节奏不携带信息，所以没有
第二种频率。不同的只有画面停留多久：`Err4` 没有窗口，因为射频死了不是等一等就能解决的；而 `Err1` 到 `Err3` 在两秒后
清除。那是它什么时候离开，不是它长什么样。三个窗口存在，是因为那些事件过去只产生一行日志、台架前的人看不到任何
东西，于是一台坏掉的装置和一台空闲的装置长得一样。**`Err3` 是监视器，不是某个事件能到达的脸**：它报告固件本不该
进入的状态（采集带着判定计时器，或判定画面没有计时器），所以看到它时没有输入可查——该查状态 bug。**`Err4` 是
`rig-ble` 构建的代码，表示射频没有启动，或者链路在一分钟内、正在通话时断了五次**——一个连上又礼貌离开的客户端不算
掉线，台架上一连串有意的连接/断开循环因此不会把装置打下线。OLED 没有代码画面，所以 `Err4` 时由它自己画
`RADIO FAULT` 和 `REFLASH RIG-SERIAL`，而且那个构建里正文行写的是 `NO LINK TO PC`，不是 `CHECK USB CABLE`。
**退役的 `Err0` 保留它的编号空着**：其余代码不重编号，而 `faultAt` 由 `Err4` 独占，所以没有东西会在警告中途重打
它的闪烁相位。

**重拍读 `F`，不是 `E`。** `E` 是每一个故障代码的开头，` 40E` 与一个 `Err` 画面只差一眼；`F` 是左列
加上上横与中横，任何代码里都没有它。

**判定是结论，不是标签。** `PASS` 与 `RETAKE` 在没有新按键 12 s 之后回到 `READY`。分数不会丢——
PC 留着记录——而一块在按下很久之后还写着 ` 95P` 的面板，看起来是卡住了而不是在等待。在这个窗口里开始的采集会
直接取消计时器：上一次判定的计时器绝不能把新的采集拉回 `READY`。**判定用主循环自己的时钟读数打时间戳**——到期
判断用的也是同一个——因为紧接着再取一次 `millis()` 可能落在读数之后一毫秒，把无符号的年龄回绕掉，让脸在出现的
那一轮就到期（`CAP` 一闪回 `READY`，就是 1.22 修的那个缺陷）。

**没有彩排了，按键只有一个含义。** 按一下就在按下沿发起一次采集，松开根本不是事件，所以故障画面只在
它的事件真的发生时出现：没有东西出故障的台架上永远看不到 `Err1` 到 `Err3`。只有脸占着屏幕时（`Pairing`、
`RadioFault`）按键才被拒绝；在 `Live` 里即使协议层已经 `Gone` 也会采集，因为安静下来的订阅者不是「没人」。这也是
那些事件既上报又显示的原因——`EVT TIMEOUT`、`EVT STRAY RESULT`、`EVT INVARIANT` 是故障另一个可见的地方。
**按键在下一轮循环才被处理**，可能排在一次约 25 ms 的整帧 OLED 发送之后；这段延迟是接受的，循环不为它重排，因为
25 ms 远在消抖窗口之内，而把按键排到链路和判定计时器前面，是拿一个看不见的延迟去换一个真实的顺序 bug
（`docs/rig-state-machine-zh.md` §11 规则 15）。

**故障压过屏幕，未知分数绝不是零。** 故障窗口盖着面板、底下的屏幕继续走，所以在窗口期间到达的判定会
丢掉它的进场扫过——等故障清掉，那 250 ms 早就过期了，动画是**被吃掉，而不是被推迟**。而分数 `-1`
——一次没有回音的采集留下的值——画成**空白加结论字母**：一次 `NO REPLY` 重拍读作 `   F`，不是
`  0F`，因为在超时旁边写一个 0，恰好编造了这次超时声称缺失的那个数字。同一个分数下 OLED 不画数字。

**字母表是数字，加上 `A`、`C`、`E`、`F`、`P` 和一个小写 `r`。** `r` 只为 `Err` 这一个词而收，故障
代码就是由它拼成的，它也是唯一被画出来的小写字母；`-` 是只有 G 段的那条空闲横杠。这个集合之外的字符
要么与数字混淆——`O` 读成 `0`、`S` 读成 `5`、`I` 读成 `1`、`G` 夹在 `6` 与 `9` 之间——要么根本画不
出来，比如 M、W、K、V、X、Y、Z。所以一个词会变成一个代码，这也是故障写成 `Err1` 而不是 `TIME` 的
原因。`main.cpp` 里的表只实现有画面在显示的东西，因为一个没人用的字形，就是下一个人断定「这个字符
可以画」的依据。

**每一个状态间隔都是 PC 保活周期（2 s）的整数倍。** 一个保活是故障窗口；两个是采集超时（**4 s**）；
五个是失联判定；六个是判定画面。它们被有意写成 `cfg::PC_KEEPALIVE_MS` 的乘积：保活一变，它们全都得
跟着变，而那是唯一一个不能单独改的数字。判定因此有意活得比失联阈值更久——链路一定会先被报出来，判定
才会自己消失。

**每一个画面间隔都是 `cfg::DISPLAY_UNIT_MS`（25 毫秒）的整数倍**，同样写成乘积：每一个除以二十五都是
整数。250 µs 的位周期属于另一个域——那是微秒级的硬件数字，不是画面间隔——25 ms 的按键消抖也不是：那个
数字相同只是巧合，不是同一套东西。

## 串口协议

一行一条消息，115200 波特率，ASCII，以 `\n` 结尾。一行最多 95 个字符：溢出时缓冲区复位，更长的输入
不会被当作一条消息处理。固件忽略它看不懂的任何内容，所以一个乱码字节不会让装置变砖。

| 方向 | 消息 | 含义 |
|---|---|---|
| → PC | `EVT HELLO <version>` | 板子起来了 |
| → PC | `EVT I2C <addr>` | 开机扫描时每个应答的设备一行 |
| → PC | `EVT SCREEN <name> <score>` | 一次屏幕变化：READY、CAPTURING、PASS、RETAKE。采集超时先发 `EVT TIMEOUT`，紧接这一条 |
| → PC | `EVT TRIGGER <millis>` | 按键被按下，一次采集开始了 |
| → PC | `EVT TIMEOUT <millis>` | 4 s 内没有等到判定；屏幕切到 RETAKE，随后发 `EVT SCREEN RETAKE -1` |
| → PC | `EVT STRAY RESULT <score>` | 没有在途采集却来了判定；该判定**没有**被采用 |
| → PC | `EVT INVARIANT <screen> <link>` | 固件本不该进入的状态——采集带着判定计时器，或判定画面没有计时器；它是监视器，线上永远不该出现 |
| → PC | `EVT PONG` | 对 `CMD PING` 的应答 |
| PC → | `CMD RESULT <score> <PASS\|RETAKE> <REASON>` | 要显示什么，仅在 CAPTURING 时有效；分数会被夹到 0–100 |
| PC → | `CMD READY` | 回到空闲屏幕 |
| PC → | `CMD PING` | 存活检查 |
| PC → | `CMD SCAN` | 重新扫描 I2C 总线，报出每个应答的地址 |

`REASON` 是一个 token：`LOW_LIGHT`、`BLUR`、`COLOR_CAST`、`NONE`、`UNKNOWN` 或 `NO_REPLY`。
`NO_REPLY` 由装置自己生成，永远不会发给装置；`UNKNOWN` 是服务端在没有任何子分数能指出原因时发的
（`server/app/rig/protocol.py`），装置遇到不认识的 token 也会存成它。

**新的订阅是一次新的对话，所以输入会被清空。** 在 BLE 上，载波在通知被打开时丢掉自己的 rx 环，解析器丢掉任何
半条线，因为上一个会话留下的残行绝不能被下一个会话的第一笔写成一条没人发过的命令
（`docs/rig-state-machine-zh.md` §11 规则 8）。

**PC 那一半现在有了**（`server/app/rig/`，P2-17）：服务端打开端口，每两秒发一次 `CMD PING`，
把 `EVT TRIGGER` 变成一次采集和一条 `CMD RESULT`，并记录装置上报的每一次屏幕变化。它自己的
状态机，以及采集失败时*什么都不发*的理由——装置随后超时会报 `NO REPLY`，而那正是事实——都在
`docs/rig-state-machine-zh.md` §9。

**链路由 PC 负责，沉默就意味着它安静了。** 装置看不出 USB 线插没插——它经桥接芯片走 UART，
没有载波信号——所以存活是协议层面的事：**只要链路开着，PC 就必须至少每两秒发一次
`CMD PING`**，而装置在十秒没有收到命令之后置上自己的 `Gone` 标志（漏掉五次保活）。

装置开机停在 `READY`，带十秒宽限，这远长于 PC 发出第一次保活所需的时间。`Gone` 不再改变任何屏幕：
安静的同伴仍然是同伴，装置停在它原本的屏幕上，按键照常工作。`rig::invariantHolds` 改守判定画面的
计时器——采集在途时不带计时器，判定画面必须带一个——一旦被破坏就上报 `EVT INVARIANT`。

**`rig-ble` 是例外，而这正是表现层的职责**（`docs/rig-state-machine-zh.md` §11）。没有中心设备
连着时，面板画 `APP` 与旋转的第四位，OLED 写 `WAITING`，因为射频确实能分辨出「还没有人来」。连上
之后又沉默的中心设备留在装置自己的屏幕上：安静的同伴不是故障，所以没有链路脸可画。表现层决定
画哪张脸——它不改变协议层上报的内容。

**判定是一次采集的答案，所以只在采集在途时接受。** 其它任何状态下的 RESULT 都会被丢弃，上报
`EVT STRAY RESULT`，并以故障窗口 `Err2` 显示；这里选择告诉 PC，而不是让它以为装置收下了。背后的
规则，以及每一个状态/事件组合，都在 `docs/rig-state-machine-zh.md`。

## 到货的那块板子定下了什么

第一块板子于 2026-11-10 烧录，第一个假设没有成立。`Serial` 指向了 S3 的原生 USB 口，于是 UART
桥只显示 ROM 的启动信息、没有任何来自 sketch 的输出——一块跑得好好的板子看上去像死的。现在
`ARDUINO_USB_CDC_ON_BOOT` 是 0，把 sketch 放到 UART0 上：一根线既能烧录也能监视，而且不需要按
BOOT 键。

`setup()` 还会扫描一次 I2C 总线，每个应答的设备打印一行 `EVT I2C <addr>`。这样，缺一块屏就会
出现在串口日志里，而不是只表现为一块空白屏——装配阶段这是最快的检查。

在板子上验证过：镜像能烧入并通过校验，固件打印 `EVT HELLO 1.1`，而没有接任何东西时 I2C 扫描
什么也不报。

**改线不必重启。** `CMD SCAN` 会重新扫描 I2C 总线并逐个上报应答的地址，所以换一根线之后只要发一行
命令，不用断电重启、也不用去等开机窗口。开机扫描是另一个看总线的机会，而它发生在任何人有机会动线
之前。

**打开串口会让板子复位。** 桥接芯片的 DTR 与 RTS 接了自动复位电路，所以任何程序一打开 `COM5`，
固件就会重启——日志从头是 ROM 启动信息，随后是一条全新的 `EVT SCREEN READY`。**这是板子在正常工作**，
但调试前值得先知道：一个连上端口后再等十一秒的读取程序，会看着装置置上 `Gone`，因为**开机先发生，
而十秒的链路计时也从那一刻开始**。要测保活，就在**保持打开的端口上**测，不要靠反复重连。

对工具有两个后果。台架检查一旦打开端口就退出，留下的是「刚开机」的装置，而不是它原本的状态。
而重启服务端等于重启板子：链路不是「重连」，是从头开始。

**OLED 已验证。** 直接接在 ESP32 上——`VCC` 接 `3V3`、`SDA` 接 `GPIO8`、`SCL` 接 `GPIO9`——
扫描报 `EVT I2C 3C`，开机画面画出来了，`CMD PING` 也答了 `EVT PONG`，所以从 PC 到板子的命令
通路和显示一样是通的。随后在没有按键的情况下从串口驱动了各个屏幕：
`CMD RESULT 94 PASS OK`、`CMD RESULT 30 RETAKE LOW_LIGHT`、`CMD RESULT 55 RETAKE COLOR_CAST`、
`CMD RESULT 20 RETAKE UNKNOWN`，以及越过十秒链路阈值后的空闲屏——现在那只改标志，玻璃上什么都不变。

**尚未验证的是四位数码管**，它还没接过线。面板在台架上的每一项表现都属于 `P3-17` 的验收，而不是
一次测量。
